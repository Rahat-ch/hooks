# Tests run the real CLI

Every test spawns the bundled CLI (`node dist/hardhooks.mjs …`) the way a Host does: a payload on stdin, the project as the working directory, and a hermetic environment (temp HOME, config and state dirs, no inherited Host variables, a controlled PATH). Projects are temp directories, repos use real git, and where a real program would be slow or have side effects (desktop notifiers, formatters, check commands, a git that hangs), a fake program on PATH records its calls and answers as told. Tests assert only what a Host or user sees: stdout, stderr, exit code, and files the CLI writes for the user (audit logs, formatted files).

This reverses the testing decision in the v1 spec (#1, "Seam 1: the dispatcher entry"), under which most tests called `dispatch()` in-process with an injected config, clock, process runner and, for dispatcher tests, test-only Hooks. The maintainer decided (#22) that tests should mirror exactly what Hosts do. An in-process seam can pass while the shipped bundle is broken: argument parsing, stdin handling, config and state lookup from the real environment, the platform's process spawning and the bundling itself all sit outside it. Injection points also invite tests of states no Host can produce (a test-only Hook that throws, a config object no file could express).

## Considered Options

- **Keep the in-process seam, with a few process-level smoke tests (the spec).** Fast and fully controllable, but it tests a wrapper-less product nobody runs, and the injected fakes drift from the real environment. Rejected by the maintainer.
- **Both, permanently.** Rejected: two ways to test every behaviour, and the in-process one is always the easier one to reach for.

## Consequences

- Tests are slower (a Node start per CLI run, about 50 ms) and run concurrently within a file to compensate. Each test builds its own sandbox, so tests never share state. vitest 4 honours `sequence.concurrent` only at the root of the config: set on a project it is silently ignored (ten 1 s tests took 10 s), so it sits at the root. The whole suite (about 1,100 tests) takes about 18 s on a 12-core Mac; more workers or per-file concurrency don't change that.
- Timed assertions measure the machine as well as the code. Under the rest of the suite's concurrent load, the plugin's overhead on an Event no Hook handles measured 100–200 ms instead of about 5 ms. Timed measurements therefore run in their own vitest project (`timing`), which starts only after every other test has finished (`sequence.groupOrder`). Elsewhere, timing bounds only check that something didn't hang, with wide margins. Load also exposed a test-side race: a fake check command that printed thousands of lines and then called `process.exit()` lost unflushed output on macOS, where stdout to a pipe is asynchronous. A fake that prints a lot and then fails sets `process.exitCode` instead.
- Behaviour that only test-only Hooks could reach is tested through real Hooks and real configs, or not at all. Each dropped case is listed in the commit that converted its file. Lost in total:
  - four dispatcher cases no real Hook can reach: a fail-open Hook that throws (every one swallows its own errors), the dispatcher's own per-Hook timeout (git's 5 s query timeout always fires before a Guard's 30 s backstop, and no fail-open Hook declares one), a PreToolUse message joined with the ask-fallback warning (no Hook sends a message on PreToolUse), and several Hooks' terminal sequences joined (only notify emits one);
  - one `hardhooks test` case, a shipped fixture file that is invalid: the bundle inlines the fixtures at build time and none is invalid. The parser is still covered through user case files;
  - the trust prompt text (`Trust <root>? [y/N]`) and answering "n" on a terminal: `hardhooks trust` asks only when stdin is a TTY, and tests pipe stdin. The listing printed before the prompt is still asserted;
  - fake formatters and notifiers only record their calls. format-on-edit tests assert that the formatter ran on the file, not that the file changed; one case runs real prettier to cover the rewrite.
- The product gets outside knobs only where real behaviour can't be arranged. So far there is one: `HARDHOOKS_NOW` (an ISO 8601 date) fixes the CLI's clock, for dates, turn lengths and audit-log days. Everything else uses real behaviour: detached notifications are awaited through the fake notifier's record file, timeouts are real time with small configured values, and trust is granted with the real `hardhooks trust --yes`.
- On Windows, a program the product spawns by bare name without a shell (git, desktop notifiers, gofmt, rustfmt, ruff) must be a real `.exe`, which can't be faked. Those cases are POSIX-only (`it.skipIf(process.platform === "win32")`). Command lines run through the shell, and Node formatters run as `node <script>`, are faked on every OS.
- Migration was expand–migrate–contract (#22): first the harness with the dispatcher and config tests, then the remaining files, then the in-process helpers (`test/helpers/`), the `unit` and `smoke` projects and the test-only injection points in `src/` were removed. That meant `hooks` on `dispatch`, `init`/`uninstall`, `trust` and `runTests`, `fixtures` on `runTests`, and `defaultConfig()`. `config` and `trusted` on `dispatch` stay because `hardhooks test` needs them: it resolves the config once for all its cases, and it judges cases by the trust of the project it runs in, since a case's payload may name another directory.
