## Development

npm, Node ≥20. `npm ci`, then `npm run typecheck`, `npm test` (unit), `npm run test:smoke` (builds `dist/hardhooks.mjs`, then spawns it). CI runs all of these on Linux, macOS and Windows × Node 20/22/24. `dist/` is build output, never committed.

- **Seam.** `dispatch()` in `src/dispatcher/` takes an Event name, the raw Host payload, an `Environment` (cwd, home, env, platform, clock, process runner, state dir) and optionally a `ResolvedConfig` (omitted, it loads config files through the `Environment`, as `hardhooks run` does), and returns `{ stdout, stderr, exitCode }`. The CLI (`src/cli.ts` → `src/commands/`) only wraps it. Tests drive `dispatch` via `runEvent` and assert only Host-visible output (`expectBlocked`, `expectAsked`, `expectNoDecision`, `expectContext`), never internals.
- **Test helpers** live in `test/helpers/`: `claudeCode.*` payload builders per Event, `fakeEnvironment()` (temp dirs removed after each test, fixed clock, recording process runner, or `processRunner: "real"` for real git in temp repos; call it inside a test), `loadFixtures`/`expectFixture` for JSON fixture payloads, `writeRepoConfig`/`writeUserConfig` to put config files where `runEvent` will load them.
- **One directory per Hook**: `src/hooks/<name>/index.ts` exports a `defineHook({...})`, beside `<name>.test.ts` and `fixtures/*.json`. Register it in `src/hooks/registry.ts`: one import and one array entry per line, sorted by name, so parallel branches merge cleanly. Same rule for commands in `src/cli.ts`.
- **Options and Presets.** A Hook declares `optionsSchema` with the DSL in `src/config/schema.ts` (`import * as s`; `s.object`, `s.boolean`, `s.string`, `s.number`, `s.oneOf`, `s.array`, `s.optional`) and `defaults: { standard, strict }`, each `{ enabled, options }` with a value for every non-optional option; `defineHook` type-checks the two against each other and `run` gets the resolved options. No `optionsSchema` means no options. Users set `hooks.<name>.{enabled, ...options}` in `.hardhooks.json` (repo, nearest up to the git root) over the user config (`${XDG_CONFIG_HOME:-~/.config}/hardhooks/config.json`; `%APPDATA%\hardhooks\config.json` on Windows): Preset defaults, then user, then repo, option by option (arrays and objects are replaced, not merged). Unknown keys or wrong types make the config invalid, which blocks wherever a Guard would run (ADR-0004). After changing any option schema run `npm run schema` to regenerate the shipped `hardhooks.schema.json` (a test fails if it drifts).
- **Hooks are Host-neutral**: they read the normalized `HookEvent` (`src/event.ts`), match tools by kind (`shell`, `edit`, ...), return a Decision from `src/decision.ts` (`block`, `ask`, `allow`, `addContext`) or `undefined`, and use `env.processRunner` for external programs. Only the dispatcher writes output; Claude Code translation lives in `src/hosts/claude-code.ts`.
- **Shell analysis** for Guards goes through `analyzeShell()` in `src/shell/`.
- **Hosts and merging.** The dispatcher merges Decisions (block > ask > allow, reasons combined) and infers the Host from payload and env with the ordered, data-driven `detectionRules` in `src/hosts/index.ts` (payload signals before env; unknown = Claude Code). `hostCapabilities` there says whether a Host honours `ask`; where it doesn't, a PreToolUse ask becomes allow plus a `systemMessage` warning under `standard` and a block under `strict`. Test other Hosts with `hostPayloadFields` (or env vars via `fakeEnvironment({ env })`) and `expectAllowedWithWarning`. A Hook may set `timeoutMs`; Guards default to 30 s and block on timeout, other Hooks have no limit and are ignored on timeout.
- **Install seam.** `init()` / `uninstall()` in `src/install/` take an `InstallRequest` (`env`, `scope: "project" | "user"`, `mode: "prompt" | "yes" | "dry-run"`, `bundlePath`, `confirm`, `stdout`/`stderr`, optional `hooks`) and resolve to the exit code; `hardhooks init|uninstall [--user] [--dry-run] [--yes]` only parse flags. Tests drive them with `runInit`/`runUninstall` against `fakeEnvironment()` temp dirs and assert the settings files (`projectSettingsPath`, `userSettingsPath`, `readSettings`, `writeSettings`) and the printed diff. Entries are exec form, `{ "type": "command", "command": "node", "args": [<bundle>, "run", <Event>] }`, one matcher group per Event, matcher = the union of `claudeCodeTools` for the enabled Hooks' tool kinds (none if any Hook handles every tool). They are recognised as ours by shape (`args` = `[…/hardhooks.mjs, "run", …]`), with no marker key. `<bundle>` is the running bundle's absolute path, or `${CLAUDE_PROJECT_DIR}/…` in project settings when hardhooks is installed in the project. Never the `hardhooks` bin: on Windows that is a `.cmd` shim, which exec form can't spawn.
- **Claude Code plugin.** The repo root is the plugin (`.claude-plugin/plugin.json`, static `hooks/hooks.json` running `node ${CLAUDE_PLUGIN_ROOT}/dist/hardhooks.mjs run <Event>` for every `EventName`). The marketplace (`.claude-plugin/marketplace.json`) installs it from the npm package via an `npm` source, because `dist/` is never committed and plugin installs never build; the npm `files` list ships the plugin files beside the bundle. Bump `plugin.json` `version` with `package.json` (installs only update when it changes). A new `EventName` needs a `hooks/hooks.json` entry. Validate the packed tarball (CI `plugin` job), not the repo root: `--strict` fails there on `CLAUDE.md`. Try it locally with `npm run build && claude --plugin-dir .`.
