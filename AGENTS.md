## Development

npm, Node ≥20. `npm ci`, then `npm run check`: typecheck, then `npm test` (vitest's globalSetup builds `dist/hardhooks.mjs` once, then every test spawns it). CI runs both on Linux, macOS and Windows × Node 20/22/24. `dist/` is build output, never committed.

- **Tests run the real CLI (ADR-0006).** Every test lives in `test/e2e/` and spawns `node dist/hardhooks.mjs …` as a Host would, asserting Host-visible output (`expectBlocked`, `expectAsked`, `expectNoDecision`, `expectContext`, `expectMessage`, `observe`) and files the CLI writes for the user. Arrange every state through real files, real configs, real git and fakes on PATH; the product has no in-process test seam (no injected Hooks, configs, clocks or process runners), and `src/` is imported only for types and the case/Decision parsers in `src/testing/` the harness shares with `hardhooks test`, never to compute an expected value. Tests in a file run concurrently (`sequence.concurrent` at the root of `vitest.config.ts`: vitest 4 ignores it inside a project), so each test makes its own sandbox; `describe.sequential` opts a block out. Timed measurements go in `test/e2e/timing/` (vitest project `timing`, run after every other test has finished, so the suite's load doesn't skew them). Harness, from `test/e2e/helpers`: `sandbox(options?)` per test gives a temp `project` (the cwd and payload `cwd`), `home`, `stateDir`, `userConfigFile` and a hermetic env (nothing inherited: no `CLAUDECODE` or other Host variables, `TZ=UTC`, PATH = fake programs, then real node and git; `systemPath: true` adds `/usr/bin:/bin`; Windows always gets System32). Its methods: `event(payload, { event?, cwd?, env?, now? })` runs `hardhooks run <Event>`, `run(args, …)` any command, `writeRepoConfig`/`writeUserConfig`/`writeFile`, `trust()` (the real `hardhooks trust --yes`; write the files it covers first), `initGitRepo(dir?, opts)` or `sandbox({ git: true })` (real git, fixed identity), `fakeProgram(name, behaviour)` (a recorded fake on PATH: exit code, stdout, stderr, `delayMs`, per-argv `rules`; `calls()`, `waitForCalls()`), `fakeProgramAt(path)`, `fakeNodePackage(pkg, bin)`, and `auditLog()` (the entries audit-log wrote: detected Host, each Hook's Decision, error and timing). Payload builders (`claudeCode.*`, `hostPayloadFields`), `hookFixtures(name)`/`expectFixture`, `copyBundle(dir)` (see Install below) and `installPlugin(box)`/`runPluginHook(box, plugin, event, payload)` (the packed plugin, run as Claude Code runs its hooks file) are exported there too. Fakes and Windows: a program the product spawns by bare name without a shell (git, notifiers, gofmt, rustfmt, ruff) can only be faked on POSIX, so those cases use `it.skipIf(process.platform === "win32")` with a comment; shell command lines (`.cmd` shim) and Node formatters (`node <script>`) are faked everywhere. Product knobs for tests, kept to the unavoidable and listed here: `HARDHOOKS_NOW=<ISO 8601>` fixes the CLI's clock (`sandbox({ now })` or `event(…, { now })`; an unparseable value is ignored). A behaviour no real file, config, program or knob can arrange stays untested rather than gaining a seam; a new knob needs a reason in ADR-0006 and a line here.

- **Dispatcher.** `dispatch()` in `src/dispatcher/` takes an Event name, the raw Host payload and an `Environment` (cwd, home, env, platform, clock, process runner, state dir), and returns `{ stdout, stderr, exitCode }`; `hardhooks run` (`src/cli.ts` → `src/commands/`) only wraps it. It loads config files and looks up trust itself; only `hardhooks test` passes the optional `config` (resolved once for all its cases) and `trusted` (the trust of the project it runs in, since case payloads may name another directory).
- **One directory per Hook**: `src/hooks/<name>/index.ts` exports a `defineHook({...})`, beside its `fixtures/*.json`; its tests are `test/e2e/hooks/<name>.test.ts`. Register it in `src/hooks/registry.ts`: one import and one array entry per line, sorted by name, so parallel branches merge cleanly. Same rule for commands in `src/cli.ts`.
- **Fixtures ship to users.** `hardhooks test` replays every `src/hooks/<name>/fixtures/*.json` against the *user's* resolved config (the build inlines them into the bundle; nothing to register). Format and validation: `src/testing/cases.ts`, shared with user case files (`.hardhooks/tests/*.json`; example in `examples/tests/`). A payload with `hook_event_name` is sent verbatim; otherwise one is built from `event` + `tool`/`input` or a shorthand (`bash`, `read`, `write`, `edit`), with the payload fields and env vars that make the dispatcher detect the case's `host` (any id in `src/hosts/index.ts`; default `claude-code`). Fixtures run with no real processes (`src/testing/sandbox.ts`: git answers "not a git repository", everything else succeeds silently), and are skipped when their Hook is disabled. When the expected Decision depends on a Preset or option value, declare it: `"assumes": { "preset": "strict", "options": { ... } }`, or the fixture fails for users who changed that option. The command is `runTests()` in `src/testing/` (tests: `test/e2e/test-command.test.ts`).
- **Options and Presets.** A Hook declares `optionsSchema` with the DSL in `src/config/schema.ts` (`import * as s`; `s.object`, `s.boolean`, `s.string`, `s.number`, `s.oneOf`, `s.array`, `s.optional`) and `defaults: { standard, strict }`, each `{ enabled, options }` with a value for every non-optional option; `defineHook` type-checks the two against each other and `run` gets the resolved options. No `optionsSchema` means no options. Users set `hooks.<name>.{enabled, ...options}` in `.hardhooks.json` (repo, nearest up to the git root) over the user config (`${XDG_CONFIG_HOME:-~/.config}/hardhooks/config.json`; `%APPDATA%\hardhooks\config.json` on Windows): Preset defaults, then user, then repo, option by option (arrays and objects are replaced, not merged). Unknown keys or wrong types make the config invalid, which blocks wherever a Guard would run (ADR-0004). After changing any option schema run `npm run schema` to regenerate the shipped `hardhooks.schema.json` (a test fails if it drifts). When one of a Hook's `events` is opt-in through an option (check's `subagentStop`, `editCommand`), also define `activeEvents(options)` returning the Events it handles with those options (default: all of `events`); `init`'s entries, `hardhooks test`'s missing-Event warnings and the dispatcher's Hook selection all go through `activeEvents()` in `src/hooks/hook.ts`, so they agree.
- **Hooks are Host-neutral**: they read the normalized `HookEvent` (`src/event.ts`), match tools by kind (`shell`, `edit`, ...), return a Decision from `src/decision.ts` (`block`, `ask`, `allow`, `addContext`, `terminalSequence`, `message`: shown to the user as `systemMessage`, never to the model; on Stop use it rather than `addContext`, which keeps the turn going) or `undefined`, and use `env.processRunner` for external programs (`spawnDetached` for side effects that must not delay the Host; `shell: true` runs a user-written command line through `sh -c` or `cmd.exe`). Only the dispatcher writes output; Claude Code translation lives in `src/hosts/claude-code.ts`, which joins into one `systemMessage`: an unblockable Event's reason, then Hook `message`s (prefixed `[hardhooks/<hook>]`).
- **Observers.** A Hook may also define `observe(record, options, env)`: once every selected Hook has run, the dispatcher hands it a `DispatchRecord` (`src/hooks/hook.ts`: the Event, resolved config, each Hook's Decision, error and duration, the final `HostResult`); it can't change the output and its errors are ignored. `audit-log` is one: its JSONL lines (`<stateDir>/audit-log/<project>-<hash>/<UTC day>.jsonl`) are `hardhooks test` cases (extra data under `audit`; `--cases <day>.jsonl` replays a day), redacted with `secretsMatcher()` and `redactSecrets()` (`src/secrets/redact.ts`, token-like values), which are tested through the entries audit-log writes.
- **Trust (ADR-0005).** Project commands run only in a project the user trusted with `hardhooks trust`. A Hook declares command-valued options in `commandOptions`: the dispatcher withholds repo-config values for them in an untrusted project, and the user config's value applies instead. Before running a command it autodetected, a Hook calls `trust.mayRun(description)`, the 4th `run` argument; on false it skips the command, and the dispatcher tells the user once per session. `projectCommands(cwd, options)` lists what it would autodetect, for `hardhooks trust` to show. Store, hash inputs and status: `src/trust/`. The command is `trust()` in `src/trust/command.ts`. A fresh sandbox is untrusted; e2e tests about a Hook's own commands write the project's files, then `await box.trust()` (the real `hardhooks trust --yes`).
- **Shell analysis** for Guards goes through `analyzeShell()` in `src/shell/`. Guards share `src/hooks/guard.ts`: they collect `Finding`s (`block` or `ask`, with a reason) and return `decide(findings)`, and block a command `analyzeShell()` can't parse with `cannotAnalyse(<hook name>, error)`.
- **Shared helpers.** Use these rather than writing another copy:
  - *Project root*: `projectRoot()` in `src/project/` (nearest ancestor holding `.git`, else the directory; paths taken as given, never resolved against the process cwd) and `searchUpwards()` for file lookups that stop at that root. Every Hook, trust, config and install use them; block-destructive-shell alone uses git's `--show-toplevel`, because it asks git about paths relative to it.
  - *Paths*: `src/paths/`. Host paths (`canonicalPath`, `resolvePath`, `relativeTo`) are platform-neutral strings (POSIX, Windows and Git Bash spellings) and always case-folded, for matching secrets. Native paths (`isWithin`, `samePath`, `resolveOperand`, `pathUnder`, `toSlashes`) use `node:path` and fold case only where `foldsCase(platform)` (Windows, macOS). They compare as written: before comparing paths from different sources (git's real path against a Host cwd reached through a symlink or a Windows 8.3 short name like `RUNNER~1`), pass both through `physicalPath()`. Never fold a path you display or store.
  - *Secrets*: whether a path holds secrets, `secretsMatcher()` / `isProtectedPath()` in `src/secrets/` (built-in patterns, project ignore files, `protect`/`allow`), shared by protect-secrets and anything else that must recognise secrets.
  - *Git*: every git query lives in `src/git/` and runs through `runGit()` (`env.processRunner`, `env.env`, `--no-optional-locks`); Hooks never spawn git for a query themselves. Informational queries (`gitStatus`, `recentCommitSubjects`, `isGitIgnored`, `workingTreeFingerprint`) take the `Environment` and return undefined outside a repo or on any failure. Guards use `GitQueries`: one per Event, cached, and it throws on a timeout so the Guard fails closed. `--porcelain=v2` output is parsed only by `parsePorcelainV2()`.
- **Hosts and merging.** The dispatcher merges Decisions (block > ask > allow, reasons combined) and infers the Host from payload and env with the ordered, data-driven `detectionRules` in `src/hosts/index.ts` (payload signals before env; unknown = Claude Code). `hostCapabilities` there says whether a Host honours `ask`. A PreToolUse ask must reach a human (ADR-0007): where the Host doesn't honour it, or the payload's `permission_mode` is one nobody answers prompts in (`auto`, `dontAsk`, `bypassPermissions`; the event's `permissionMode`), `askFallback()` in `src/dispatcher/` turns it into a block under both Presets, adding the reason from `unansweredAskReason()` in `src/hosts/` and telling the agent to have the user run it. Test other Hosts with `hostPayloadFields` (or env vars via `sandbox({ env })`) and modes with `claudeCode.bash(cmd, { permission_mode })`; `box.auditLog()` shows the Host detected. A Hook may set `timeoutMs`; Guards default to 30 s and block on timeout, other Hooks have no limit and are ignored on timeout.
- **Install.** `init()` / `uninstall()` in `src/install/` take an `InstallRequest` (`env`, `scope: "project" | "user"`, `mode: "prompt" | "yes" | "dry-run"`, `bundlePath`, `confirm`, `stdout`/`stderr`) and resolve to the exit code; `hardhooks init|uninstall [--user] [--dry-run] [--yes]` only parse flags. Tests (`test/e2e/install.test.ts`) run `box.run(["init", ...], { stdin: "y\n" })` and assert the settings files in the sandbox's project and home and the printed diff; the built bundle stands for a global install, and `copyBundle(<project>/node_modules/hardhooks)` plus `box.run(args, { bundle })` for a project-local one (`init` refers to the bundle it runs from). Entries are exec form, `{ "type": "command", "command": "node", "args": [<bundle>, "run", <Event>] }`, one matcher group per Event, matcher = the union of `claudeCodeTools` for the enabled Hooks' tool kinds (none if any Hook handles every tool). They are recognised as ours by shape (`args` = `[…/hardhooks.mjs, "run", …]`), with no marker key. `<bundle>` is the running bundle's absolute path, or `${CLAUDE_PROJECT_DIR}/…` in project settings when hardhooks is installed in the project. In project scope, `${CLAUDE_PROJECT_DIR}` entries go in the shared `.claude/settings.json`; an absolute path never does (on a teammate's machine it fails with a non-blocking error, so their Guards silently do nothing), so those entries go in `.claude/settings.local.json` (per machine; every supported Host reads it), and init removes ours from the other file so nothing runs twice. Never the `hardhooks` bin: on Windows that is a `.cmd` shim, which exec form can't spawn.
- **Claude Code plugin.** The repo root is the plugin (`.claude-plugin/plugin.json`, static `hooks/hooks.json` running `node ${CLAUDE_PLUGIN_ROOT}/dist/hardhooks.mjs run <Event>` for every `EventName`). The marketplace (`.claude-plugin/marketplace.json`) installs it from the npm package via an `npm` source, because `dist/` is never committed and plugin installs never build; the npm `files` list ships the plugin files beside the bundle. Bump `plugin.json` `version` with `package.json` (installs only update when it changes). A new `EventName` needs a `hooks/hooks.json` entry. Validate the packed tarball (CI `plugin` job), not the repo root: `--strict` fails there on `CLAUDE.md`. Try it locally with `npm run build && claude --plugin-dir .`.
